数据中台-元数据管理
背景：数据中台初期对元数据的理解应用只是简单的归纳为关系型数据库中定义的字段及描述，在这种情况下，元数据存在数据分散、数据质量低下，缺乏标准化以及元数据，因此需要有标准的元数据管理系统；
目标：基于元数据管理理论开发一套元数据管理系统
行为：在这个过程中学习了元数据理论，了解到元数据（Metadata）是数据的数据，即描述数据的数据，它提供了数据的上下文、结构和含义，是数据治理、数据管理和数据共享的核心基础。
	归纳了元数据的定义，包括数据的类型、格式、结构（如表名、字段类型），数据存储的位置（如数据库表、文件路径），数据的所有者、使用者、权限，数据的更新频率、版本历史，数据的业务含义、敏感级别、合规要求。
	总结了核心价值，1. 数据发现与可访问性，通过元数据目录，快速定位所需数据 2. 数据治理与合规，标记敏感数据（如 PII）、定义数据质量规则（如字段非空）3. 协作与知识共享，统一团队对数据的理解，减少沟通成本，避免“数据歧义” 4. 自动化与效率提升，定时提取元数据实现元数据更新
	梳理了元数据常见类型，如下：
		1. ​技术元数据：描述数据的技术属性（如存储结构、ETL流程），如表的创建时间、字段数据类型、索引信息；
		2. ​业务元数据：描述数据的业务含义和用途（如数据归属部门、业务指标定义），如设备稼动率、设备总运行时长
		3. ​管理元数据：描述数据的治理规则（如权限、分类标签），如数据敏感级别标记为 PII
​		4. 操作元数据：描述数据处理过程（如 ETL 作业日志、任务依赖关系），如Flink 任务的执行时间、输入输出数据量
​		5. 术语元数据：定义数据字典和标准化术语
	调研了多个元数据管理工具，​Apache Atlas、DataHub、OpenMetaData，分析了各工具的优劣势
结果：数据中台元数据管理模块开发完成

系统思考
背景：数据中台由多个模块组成，包括数仓建模、数据集成、数据开发、数据服务等模块，这些模块当时都自行管理元数据，这就造成每个系统对元数据的定义存在不一致的情况，且各平台对元数据更新策略也存在不同，造成数仓建模更新的元数据信息在数据开发、数据服务中未及时更新；或者数仓建模中更新了元数据信息，但数据开发中应用元数据的配置发生了变化，引起数据开发已经定义的流程报错；同时各系统都要为各种数据源去适配提取元数据信息，造成开发工作量重复，资源浪费，因此多模块对接统一的元数据管理很有必要
目标：数据中台的多个模块对接元数据管理
行为：整理了各平台应用的数据源，对数据源主要分为了三大类，关系型数据库、消息队列以及其他数据源，其中关系型数据库实现了MySQL、Postgres、Oracle、SQLServer、Doris和Clickhouse元数据的配置及提取，包括数据源连接、数据库、Schema、表、字段等信息；消息队列实现了Kafka元数据的管理，包括Kafka的连接、Topic等信息；其他数据源实现了Http、Redis、Mqtt等用户自定义的连接信息管理；其他模块不再需要为各种数据源的元数据进行适配，基于元数据管理模块提供的Api 接口即可获取各种数据源的元数据定义，同时根据各模块的应用元数据的行为，进行了如下设计：
1. 低代码底座：低代码底座管理的数据源连接信息统一推送到元数据，以支持IOT、数据中台、BI对数据源连接信息的应用；
2. 数仓建模：数仓的分层定义设计的元数据同步到元数据，数仓的元数据信息变化也会进行记录，形成了版本管理；
3. 数据集成、数据开发和数据服务：统一从元数据管理模块获取对应数据源元数据信息，基于元数据来进行相应操作。
结果：数据中台的数仓建模、数据集成、数据开发和数据服务模块都完成了对接元数据管理

严谨细致
背景：元数据准确性是数据治理的核心目标之一，直接影响数据的可信度、可用性和业务决策的有效性，不准确的元数据可能导致数据发现错误、血缘分析失效、合规风险甚至业务损失。
目标：基于元数据实现对数据质量管理
行为：总结了元数据准确性定义，元数据准确性指元数据描述的数据特征（如字段类型、业务含义、存储位置等）与实际数据的一致性和正确性；
归纳了元数据准确性的重要性可分为以下几点：
	1. ​数据可信度：准确的元数据是数据资产化的基础，避免“垃圾进，垃圾出”。
​	2. 高效查询：通过准确的标签和术语，快速定位所需数据（如搜索 #销售 表时不会返回无关数据）。
	3. ​合规审计：确保敏感数据标记正确，满足 GDPR、CCPA 等法规要求。
​	4. 血缘分析：准确追踪数据依赖链，避免因元数据错误导致的生产故障。
	5. ​成本优化：减少因元数据错误引发的数据冗余、存储浪费或重复开发。
归纳了元数据不准确造成的影响如下：
	1. ​数据定义错误，如字段类型定义错误，会造成ETL 处理失败、查询性能下降
	2. 术语不一致，如同一业务概念在不同系统中有不同名称，会造成跨团队协作效率低、数据重复录入
	3. ​元数据过时，如数据表结构变更后未更新元数据（如新增字段未同步到目录），会造成遗漏关键数据依赖
​	4. 敏感数据标记遗漏，如未正确标记 #GDPR 数据，导致合规风险，会造成法律罚款、数据泄露事件
​	5. 多源数据冲突，如同一数据资产在多个系统中元数据描述不一致（如数据库表 vs. 数据湖），会造成数据使用混乱、分析结果偏差
​	6. 缺乏校验机制，如未对元数据进行自动化验证（如字段格式、枚举值），会造成错误数据流入下游系统
为保障元数据准确性，提供了统一的数据模型来定义元数据结构，确保字段类型、关系和约束的一致性；提供了术语管理，建立企业级术语表，统一业务术语；提供了自动化元数据采集与同步服务；实现了数据验证与校验的数据质控功能。
结果：元数据管理模块开发完成

体系设计与搭建
背景：数据治理体系是企业构建数据驱动文化的基础框架，其核心目标是确保数据资产的安全性、一致性和可复用性，数据中台基于数据治理体系由此而诞生。
目标：实现数据中台的研发
行为：
	1. 参与数据架构设计，定义数据的逻辑与物理结构，明确数据源、存储层和应用层的映射关系，定义数仓分层架构：ODS（原始数据层）、DWD（明细数据层）、​DWS（汇总数据层）、ADS（应用数据层）、DIM（统一维度库）；
	2. 开发元数据管理的标签、术语实现根据数据敏感性、业务价值或合规要求对数据进行分类，如根据敏感度定义 PII 术语对数据进行定义、根据业务领域定义相关标签对数据进行分类
	3. 通过元数据管理构建企业级数据目录，实现数据资产的可发现性和可管理性，包括采集整合多源数据的元数据、提供快速检索元数据
	4. 开发数据质控实现数据质量管理，确保数据的准确性、完整性、一致性
	5. 开发数据开发流批一体模块实现数据清洗和数据存储
结果：数据中台已应用多项目且保持高频的迭代优化

数据应用服务
背景：指标管理是数据治理与业务分析的核心环节，旨在通过标准化、自动化和可复用的方式定义、采集、分析和应用数据指标。
目标：实现指标口径管理确保指标定义、计算逻辑和数据源的唯一性，通过对原始数据加工得到的量化结果，用于衡量业务目标，支持灵活的组合维度（如时间、地域、业务部门等）对指标进行深度分析，支撑决策优化。
行为：
	1. 参与设计指标定义与分类（原子指标、复合指标）；
	2. 参与指标口径管理实现指标定义、计算逻辑和数据源的唯一性；
	3. 开发多维度指标查询，该查询支持交叉分析，通过多个维度的组合对指标深度分析；支持动态过滤，允许用户按需调整维度；
	4. 在数据模型是星型模型的情况下，即由事实表和维度表构成的复杂数据形态，多维度指标查询实现了对星型模型数据的查询，即支持按事实表中的维度进行维度查询，也支持按照维度库中的维度进行查询，同时也支持事实表维度和维度库维度组合查询，为优化性能，实现了通过对星型模型数据构建指标维度索引树，加速指标查询；
	5. 多维度指标查询同时完成同BI平台的对接，实现用户自定义维度即可获取相应报表、看板等能力；
	6. 定义了统一指标查询接口，并形成该模块的标准化文档，多项目应用指标均基于该文档进行应用指标。
结果：指标管理模块开发完成

数据平台开发
背景：在用户数据量较大，轻量级的数据计算引擎较慢的数据处理是不能被用户接受的；在业务形态复杂的情况下，业务会即存在批任务计算也存在流任务的需求，单一只支持批任务或流任务的框架是无法满足用户的需求；同时部署两套系统来支持流批任务，无法复用计算资源。
目标：实现数据开发流批一体数据平台，通过统一编程模型和架构设计，实现了实时与离线数据的高效协同，能够显著提升数据处理的灵活性、效率和可扩展性。
行为：主导数据开发流批一体数据平台的架构及方案设计，采用统一计算引擎Flink基于统一Api实现流批统一编程模型。
	1. 开发了基于Flink的可视化解释器，实现了用户通过可视化画布配置任务流程，可视化解释器将自行对画布配置进行解析成Dag，根据Dag转换成相应的Flink执行逻辑，完成任务执行逻辑；解释器采用统一Flink Api实现流批任务，因此基于一套Api可实现算子复用，提升了效率，同时也提高了开发的灵活性和扩展性；
	2. 开发了基于Flink SQL的解释器，实现了用户只需要编写一组SQL即可实现任务流程，SQL解释器支持大部分Flink SQL语句，会自行对一组SQL进行转换成Flink执行步骤，实现任务运行；
	3. 开发了Flink 执行工具，对Flink命令进行了封装，开发人员只需要调用Flink执行工具，传入相应的参数即可完成Flink 任务的启动运行、停止等功能
	4. Flink Client部署，基于官网发布的Flink二进制包，扩展了lib、conf、plugins等
	5. Flink Standalone 运维部署，基于官网发布的Flink二进制包，扩展了lib、plugins，调测conf下配置
结果：数据开发流批一体模块1.7版本开发完成

数据安全与隐私
背景：元数据数据安全与隐私是数据治理的核心议题，尤其在数据资产化、共享和分析日益频繁的今天，元数据的安全性和隐私保护直接影响数据可信度、合规性及业务决策的可靠性。
目标：元数据数据安全与隐私是数据治理的“隐形防线”，需通过 ​技术防护​（加密、访问控制）、流程规范​（合规审计、权限管理）和 ​文化建设​（安全意识培训）构建三位一体防御体系。
行为：调研了元数据安全与隐私的核心问题，并针对这类问题在系统中进行控制：
	1. 元数据泄露，如敏感元数据（如数据主人、访问权限、数据血缘关系）被非法获取，开发了访问控制与权限管理，调用元数据模块都需要进行身份认证，并提供了权限策略定义，用户和角色被授予了相应的权限策略才可进行数据查看；
	2. ​未授权元数据修改，如未经授权的用户篡改元数据定义（如字段类型、业务规则），导致数据不一致，元数据的权限策略支持Add、Edit、Update三种操作范围，只有被授予相应权限的用户和角色才可进行相应操作；
​	3. 隐私合规风险，如元数据中记录的敏感信息（如用户行为标签）未合规处理，违反 GDPR、CCPA 等法规，元数据管理实现了标签术语管理，通过在标签术语中定义给相应元数据定义标签术语，可在应用数据的时候保证数据的隐私性；
​	4. 技术漏洞，如元数据存储或传输中的加密不足、弱权限策略、未修复漏洞（如 SQL 注入），已实现对落库的敏感数据加密存储，对元数据管理的代码中实现了防SQL注入机制
结果：元数据管理加密存储落库敏感数据、数据设置了访问控制与权限管理

流程与数字化管理
背景：流程与数字化管理是现代企业实现高效运营、敏捷决策和可持续发展的核心战略，通过将传统业务流程与数字技术深度融合，企业能够重构工作流、优化资源配置并驱动创新。
目标：​流程数字化，将线下业务流程转化为线上数字系统，通过自动化、标准化和智能化提升效率；数字化管理，基于数据和技术构建管理决策体系，实现资源优化、风险预警和动态调整。
行为：1. 元数据管理实现了自动采集多类型数据源，支持多种关系型数据库，如MySQL、Postgres、Oracle、Doris和Clickhouse，采集信息包括数据库、Schema、表、视图、字段等信息；支持消息队列，如Kafka，采集的信息包括Topic、分区以及配置信息等；
2. 开发实现了基于表的元数据的数据质量检测和校验，规则包含是否包含指定字段、字段数量、行数范围等规则，自动对数据执行表元数据检测和校验规则，生成数据质量数据；
3. 开发实现了基于字段的元数据的数据质量检测和校验，规则包含数据是否在指定范围以内，如年龄在1-120之间，不在此范围则是异常数据；数据的长度；数据值是否在指定数据集中；数据是否符合指定正则表达式等，自动对数据执行字段元数据检测和校验规则，生成数据质量数据；
4. 开发了校验规则集，通过将多个不同检测和校验规则组合，最终自动生成一个校验规则图表。
结果：数据中台实现以数据驱动决策
